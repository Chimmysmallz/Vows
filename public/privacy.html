Information used for the wedding

Couple accounts use Firebase Authentication. Wedding details include names, dates, story, venues and optional published gift bank details. The couple may add guest names, contacts, seats, ceremony access, seating and invitation codes. Guests may submit RSVP/request notes, gift or aso-ebi transfer claims. Amounts are manually verified, not bank-connected. Stationery orders can include names, seating, a transfer receipt and proof/delivery details.

Helpers receive only their permitted wedding-operation records. They do not receive the owner's private financial records through helper access. The couple's intentionally published bank details remain visible to anyone with the wedding link. Do not put private guest lists, receipts, medical notes or order briefs in public Hosting.

Optional Google Drive photos

The wedding owner can separately authorize the app to use one owner-only private My Drive folder. The integration requests only Google's drive.file scope, not whole-Drive access. Refresh tokens and all private photo records are AES-GCM encrypted in a server-only Cloudflare D1 database using a Worker secret; the OAuth client secret stays server-side. Administrators with sufficient Cloudflare privileges may technically access backend data and keys: this is not end-to-end encryption.

Google Picker needs a short-lived access token in the authenticated owner's browser. It is used transiently, not given to guests or persisted publicly. Guests upload via Vows.ng without Google login. Original files are sent unchanged through the operator's Cloudflare Workers Free backend in bounded chunks to the couple's selected Drive folder. Originals may contain EXIF, location and identifiable people. Upload only photos you have permission to share; avoid sensitive or unwanted images.

Uploads, viewing and original downloads are owner-controlled, independent settings. All default off; downloads require viewing. When viewing is enabled, anyone able to access the published wedding link may see eligible Vows.ng-uploaded photos. Links can be forwarded; photo access is not invitation/RSVP-verified. Other pre-existing folder files are not imported or listed. Reconnect/folder change starts a new gallery binding.

View-only proxies Google-generated thumbnails, capped at 128 KiB, rather than originals. This source does not decode images or promise metadata stripping, fixed pixel dimensions or removal of sensitive visual details. Missing or unsafe previews fail closed; originals are never a fallback. HEIC originals have no preview in this MVP. Visible previews can still be saved or screenshotted. When original downloads are allowed, recipients receive the unchanged original including any original metadata. The app does not make the Drive folder public or alter sharing; folder ownership/privacy is rechecked before protected photo operations. An owner can independently share a photo through Google Drive outside these controls.

Access and abuse-control data

The backend stores encrypted wedding-bound file metadata and Google-reported whole-file SHA-256 checksums in D1; originals remain in the couple’s Drive. It hashes each bounded upload chunk for retry consistency, not the complete original. Google thumbnails are proxied with current photo authorization and are not stored in a local preview cache. The backend also stores single-use OAuth state, expiring guest capabilities/upload sessions and durable count/byte reservations. Application network identifiers are HMAC-keyed hashes rather than raw IPs. The hosting/cloud provider can log request metadata and IPs separately. OAuth browser binding uses a necessary secure HttpOnly SameSite=Lax __Host-vows-oauth cookie, cleared on success or after ten minutes. The initiating owner tab also retains a random, single-use connection verifier in sessionStorage; the final link requires this verifier, an opaque callback completion secret and fresh owner sign-in. Firebase Auth uses its normal sign-in storage. No advertising tracker is added by this integration.

The implementation deliberately does not log Google tokens, upload bodies, client secrets or upstream error objects. The operator must review actual platform logs and exclude/redact callback query URLs that may contain one-time Google authorization codes/state, restrict access and set retention.

Retention and deletion

[OPERATOR: COMPLETE ACTUAL RETENTION, BACKUP, LOG AND RESPONSE POLICIES BEFORE PUBLICATION]. Disconnect immediately blocks subsequent app photo requests and removes the usable refresh token from the live encrypted D1 connection row, then attempts Google grant revocation. It does not delete originals from the couple's Drive, previous metadata/sessions, historical backups/logs or downloaded copies. A Google grant can be revoked separately in Google Account third-party connections.

States/capabilities/session/rate records expire for authorization. A bounded Worker cron deletes up to 250 expired D1 rows every ten minutes; shared quotas or a backlog can delay physical cleanup. No paid Firestore TTL is used. Lifetime wedding-budget and gallery records have no automatic cleanup. Google upload sessions may outlast local authorization. Deleting a wedding document does not cascade to subcollections or Drive files. Failed in-flight uploads can leave private orphan files in the selected folder. The couple/authorized operator must handle any reviewed deletion request and manually review/delete those files as appropriate. No automatic 24-month deletion or fixed response-time promise is implemented.

Unpublish, disconnect, changed permissions or reconnect block subsequent requests and invalidate prior sessions. A response already delivered, browser cache already received, screenshot or downloaded copy cannot be recalled. Previously issued Firebase Storage token URLs require separate revocation and are not repaired by this integration.
