# Vows.ng: free-tier photo backend setup

**Source candidate, not a deployment. Updated 18 October 2026.** No accounts were connected, billing enabled, packages installed, or services deployed to produce this release. The previous `vows-drive-release.zip` uses Blaze and is superseded for this budget. Do not deploy it. This edition uses Firebase **Spark** for the existing website and Cloudflare **Workers Free + D1 Free** for optional Google Drive photos. There is no paid fallback.

## 1. Cost guardrails before you start

- Keep Firebase on Spark. Do not upgrade to Blaze. Do not attach a Cloud Billing account, create Firebase Functions, enable Secret Manager, enable Storage uploads or Firestore TTL. Existing legacy Storage URLs need separate revocation as described in `feature-setup.md`.
- Create/select a Cloudflare **Free** account and **Workers Free**, not Workers Paid. D1 has a Free allocation. Do not add R2, Images/Transformations, paid Durable Objects or paid add-ons. The intended route does not require a billing card. If any console requires payment/billing for a step, **stop** rather than accept it or substitute a paid service.
- Check the live official policies before using real guests. Workers Free currently permits 100,000 requests/day, 10 ms CPU per invocation, 128 MB memory and 50 subrequests/invocation: <https://developers.cloudflare.com/workers/platform/limits/> and <https://developers.cloudflare.com/workers/platform/pricing/>. This code does not raise these limits. Network waiting is not CPU time; cryptography/JSON/stream callbacks still consume CPU.
- D1 Free currently includes 5 million rows read/day, 100,000 rows written/day, 5 GB total account storage, with a **500 MB per-database** Free limit: <https://developers.cloudflare.com/d1/platform/pricing/> and <https://developers.cloudflare.com/d1/platform/limits/>. Index updates, guards, retries and cleanup count toward actual usage. On Free, exhaustion denies operations rather than creating a paid overage. Do not upgrade to continue service.
- Firebase Firestore Spark currently includes 50,000 document reads/day, 20,000 writes/day and 1 GiB storage, shared with the core website: <https://firebase.google.com/docs/firestore/quotas>. Photo checks deliberately read current weddings repeatedly, including per chunk. Photo traffic can exhaust **shared** Firestore quotas and affect core features too. No claim that core always survives shared Firebase quota exhaustion is made. A missing/off photo backend does not itself disable core code.
- Google's standard Drive API currently has no additional cost; Drive storage quota applies. The official limits page describes project quota changes since May 2026 and planned late-2026 billing-threshold/egress changes with notice: <https://developers.google.com/workspace/drive/api/guides/limits>. Leave Google Cloud billing unlinked, do not request paid quota increases, and stop if billing is demanded. This is not a promise that Drive API policy will remain free forever. Other projects/app usage and future policy matter.
- An app allowance of 2,000 reserved originals/5 GiB per wedding is **not** provider capacity. At 1 MiB/chunk, 1,000 photos of 5 MiB require at least 5,000 upload POSTs plus browser CORS preflights, capabilities, reservations, gallery/media and OAuth calls. Each photo POST invokes multiple indexed D1 operations and live Firestore reads; durable rate limits do not prevent all provider-limit exhaustion. Shared Free limits can stop photos well before the nominal wedding allowance. Failed reservations consume quota.

## 2. What to edit, and what never belongs in public/

Unzip the complete release into your own project folder. Preserve `public/` as the only Firebase Hosting public directory. Use `vows-app.html` and `vows-guest.html` as full replacement downloads; identical copies are already at `public/app.html` and `public/wedding.html`. Keep `owner-drive.js` and `guest-drive.js` synchronized if you edit the readable snippets; snippets are embedded, not separately loaded.

Never put Worker source, migrations, real `.dev.vars`/`.env`, keys, account credentials, tokens, tests, rules, configuration, private guest lists, receipts or order briefs in `public/`. No real credentials are shipped. Firebase web config, Google client ID, project number and browser API keys are identifiers, not service-account secrets. Restrict them as below. Store the OAuth client secret and encryption key only as Worker secrets.

## 3. Existing Firebase Spark project

1. In your own Firebase project, confirm **Spark**. Enable the existing Email/Password sign-in and configure only your actual authorized Hosting domains. Follow `feature-setup.md` for the complete six-feature data/role setup and legacy privacy migration. This backend does not replace those steps.
2. Replace every Firebase web-config placeholder in the full owner and guest HTML with **your** project values, then keep root/public counterparts identical. Do not reuse staging identifiers from an earlier source. The baseline source has no authorization to deploy any project.
3. Both `firebase.json` and `firebase.core.json` contain Hosting/rules only, no Functions declaration or `/api/drive/**` Function rewrite. The frontend calls the explicitly configured Worker origin. A missing Worker configuration fails the optional photo panel; it never calls an old Functions backend.
4. Firebase CLI deployment, if you choose after testing in your own environment, is explicitly limited to `firebase deploy --only hosting,firestore:rules,firestore:indexes`. Read the existing feature guide and emulator-test rules before doing this. No deployment was run here. Storage remains unused for new uploads; separately review applying the restrictive `storage.rules` to any pre-existing bucket.
5. The Worker needs a nonsecret Firebase web API key that permits **Identity Toolkit API** (`identitytoolkit.googleapis.com`). A browser HTTP-referrer-only key may fail from Worker outbound requests. Use a separate appropriately API-restricted nonsecret key for the Worker if necessary; do not weaken unrelated browser keys. `accounts:lookup` accepts the caller's Firebase ID token, not an Admin/service-account key: <https://firebase.google.com/docs/reference/rest/auth/>.
6. The Worker validates token project/issuer/expiry, calls `accounts:lookup` to validate the signed token/live account, checks UID/disabled/`validSince` against authentication time, then reads the actual wedding via Firestore REST under the same ID token. Helpers are not owners. Anonymous guest reads use the existing published-safe Firestore rules, with the legacy registry safety guard checked again in the service. Emulator and real revoked-user testing remain mandatory.

## 4. Create Cloudflare Free resources (your own environment)

Use the official Cloudflare dashboard or an already installed, reviewed Wrangler CLI in **your** environment. No CLI or package was installed for this release. Consult current official setup commands if your CLI differs; never approve a paid-plan prompt.

1. Create a Cloudflare Free account, select Workers & Pages, confirm Workers Free, and choose your `workers.dev` subdomain. Your backend origin will be `https://vows-free-photos.YOUR_SUBDOMAIN.workers.dev` (or the exact Free Worker name you choose). No custom domain or routing purchase is needed.
2. From `worker/`, create the database: `wrangler d1 create vows-free-photos`. Copy the returned UUID into `database_id` in `wrangler.toml`; retain binding **DB**. The name must match. This step creates only your Free database, not an application deployment.
3. Review `migrations/0001_private.sql`. It creates encrypted private key/value rows, versions, an expiry index and an atomic-transaction guard table. Apply only after review: `wrangler d1 migrations apply vows-free-photos --remote`. Local validation can use `--local`; the native SQLite tests supplied here do not claim to emulate D1's network/runtime semantics.
4. Edit `worker/wrangler.toml`:
   - `FRONTEND_ORIGIN`: exactly one HTTPS Firebase Hosting origin, no trailing slash/path, e.g. `https://your-project.web.app`. Use the same origin consistently. The alternate `firebaseapp.com` hostname is not automatically allowed.
   - `BACKEND_URL`: exactly the HTTPS `workers.dev` origin, no trailing slash/path.
   - `FIREBASE_PROJECT_ID` and `FIREBASE_API_KEY`: your Spark project and the nonsecret API-restricted key above.
   - `GOOGLE_CLIENT_ID`, `PICKER_KEY`, `GOOGLE_PROJECT_NUMBER`: from the Google setup below.
5. Generate an encryption key **locally**, not on a website: `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"`. Put the 32-byte base64 value into `wrangler secret put DRIVE_KEY` via its prompt. Do not commit or send it. Put the OAuth secret into `wrangler secret put GOOGLE_CLIENT_SECRET` via its prompt. The source includes no real key/secret. Keep a secure recovery copy and access policy; losing/rotating the key without re-encryption makes existing encrypted rows unreadable and owners must reconnect. There is no automatic key migration.
6. The scheduled trigger runs every ten minutes and deletes at most 250 indexed expired D1 rows per invocation. It is not paid Firestore TTL. Monitor backlogs, row/storage quotas and actual schedules. Lifetime wedding budgets/gallery metadata persist until an authorized administrator's reviewed deletion process; deleting a wedding is not cascading cleanup.
7. Before any real launch, perform section 8. Only after review in your environment: `wrangler deploy` from `worker/`. **This release did not execute it.** Confirm the account still says Workers Free afterward. Do not enable observability/log collection that records OAuth callback query strings or request secrets; review platform log defaults and retention.

## 6. Owner connection and guest behavior

- Owner signs into Firebase, saves the wedding and clicks Connect. The initiating tab creates a random verifier in `sessionStorage`, submits only its SHA-256 hash with owner auth, then navigates to a one-use Worker handoff. Worker sets a Secure/HttpOnly/SameSite=Lax `__Host-vows-oauth` cookie on its own top-level origin and redirects to Google's authorization-code+PKCE flow.
- Callback checks cookie, one-use state, original live Firebase session and generation, but **does not link an account or exchange a token**. It redirects to the fixed frontend with a random one-use completion secret in the URL fragment. Only the original tab can complete using its retained verifier **and fresh same-owner Firebase ID token**. This prevents forwarding an authenticated attacker's handoff from linking a victim's Google account. Opening in another browser/tab, clearing tab storage, or interrupted OAuth can require starting Connect again. Completion removes the fragment before the API call.
- Google offline refresh tokens, OAuth state/code, capabilities, resumable session URIs, metadata and quota records are encrypted server-only D1 values with AES-GCM/WebCrypto, context-bound by row. They are not stored in public Firestore/Hosting. Administrators with access to both keys and data can decrypt them; not end-to-end encryption. Only the owner receives an in-memory short-lived Google access token for Picker.
- Owner uses Picker to authorize/select an accessible **owner-only private My Drive folder** under `drive.file`. Shared folders/drives are rejected. The backend rechecks ownership, writability and permissions; it never creates public sharing. Existing folder contents are never imported. Reconnect or changing folder starts a new connection/gallery.
- Uploads, gallery viewing and original downloads independently start **off**. Downloads require view. Saving settings invalidates old capabilities and pending sessions. Viewing means **anyone with the published wedding link**, including forwarded recipients, can see eligible Vows uploads; invitation/RSVP verification is not used for photos. Screenshots and browser-saving visible previews cannot be prevented.
- Guests receive an expiring wedding/network-bound opaque capability and need no Google sign-in. Original upload max **20 MiB**; JPEG, PNG, WEBP or HEIC only. No SVG, HTML or video. Only type, size and header/magic are validated, not full image decoding or malware scanning. Do not claim full codec validity, decompression-bomb detection, animation rejection, content moderation or metadata removal.
- Originals pass through server-proxied Google resumable sessions in **1 MiB chunks**, except the final chunk. Upload URI/token never reaches guests. Chunk SHA-256, persisted offsets/CAS leases, Google status reconciliation and same-tab retries prevent duplicate chunk creation after a lost response. Six attempts per current chunk; capabilities last two hours, upload sessions fifteen minutes. Reload loses the browser's selected file/session; reservations are not refunded. No full-file buffering/hash or Sharp on the Free Worker.
- On completion the backend binds metadata to wedding, owner, connection, private folder, file ID/app properties, exact size/type, Google Drive version and Google-reported SHA-256 checksum. Only current-connection Vows-created originals are listed. A changed/moved file/version fails closed rather than silently refreshing.
- View-only proxies the authenticated Google-generated `thumbnailLink` through an exact HTTPS Google-host allowlist, no redirects, allowed JPEG/PNG/WEBP magic, max **128 KiB**, private/no-store/nosniff. No original fallback, fixed-pixel guarantee or local decoder. Google may omit thumbnails or use an unsupported host/format: preview fails safely. **HEIC has no preview**, even if Google happens to offer one; original downloads only if enabled. Google's temporary thumbnail details: <https://developers.google.com/workspace/drive/api/reference/rest/v3/files>.
- Enabled original downloads are streamed from Google with exact declared size and bounded stream counts, attachment/nosniff headers; the Worker does not rehash an entire original. Metadata version/checksum is rechecked first. Disable/unpublish/disconnect stops subsequent requests, not already-delivered bytes or an in-flight stream. An in-flight chunk can leave a private orphan when final publication checks fail. Review/delete orphan Drive files manually.

## 7. Durable budgets and failure behavior

The D1 adapter performs indexed version reads then an **atomic D1 batch** whose CHECK guard verifies every read version before writing. A concurrent mismatch rolls back the entire batch and retries; no in-memory quota reset across isolates. This provides atomic D1 reservations, leases, one-use OAuth state and idempotency, not a cross-provider transaction with Firestore/Google. Current Firestore publication and connection settings are rechecked before gallery publication/media exposure; unavoidable in-flight provider races cannot recall delivered data.

App limits: per wedding 2,000 reserved originals / 5 GiB lifetime; per capability 20 / 160 MiB; per network 2,000 / 10 GiB per day; project 4,000 / 10 GiB per day. Read reservations: wedding 30 GiB lifetime, project 100 GiB/day, capability 512 MiB. A preview reserves 128 KiB, originals reserve recorded size. Read/failed reservations are not refunds. Durable daily request/issuance/network limits appear in `worker/service.mjs`; they are lower-level application ceilings, not predictions of Free D1 capacity. Even after skipping a redundant successful lease-release write, 1,000 five-chunk photos require roughly 73,000 or more row mutations for prepare/chunk paths alone, before capability creation, gallery/preview requests, cleanup, indexes or conflict retries. This illustrative lower bound is not a measured production quota estimate; D1 writes can exhaust before Worker requests. The API returns an unavailable/rate-limit error and never provisions paid infrastructure. Provider-enforced quota responses may happen before the handler runs; browser panels still fail gracefully.
